# TEKSHER HUB

Внутренняя платформа знаний оператора маркировки товаров с раздельными контурами нормативной информации:

- **МЗКМ / РФ** – законодательство Российской Федерации и материалы внешнего контура маркировки.
- **ГАИС МТ / КР** – законодательство Кыргызской Республики и внутренний контур национальной системы.
- **ЕАЭС** – наднациональные соглашения, решения ЕЭК и трансграничные процессы.

## Стек

- Frontend: React, Vite, Lucide, CSS.
- Backend: Java 21, Spring Boot 3.5, Spring Security, JWT.
- Database: PostgreSQL, schema migrations with Flyway.
- Files: private server-side storage, maximum upload size 30 MB.
- Deployment baseline: Docker Compose; frontend can be hosted on Netlify.
- CI: GitHub Actions builds frontend and runs Maven verification for backend.

## Реализованные возможности

### Документы
- Создание, просмотр, редактирование и удаление карточек с реквизитами.
- Импорт материалов из CSV для ADMIN/EDITOR: до 100 строк за запрос, предварительный просмотр, результат по каждой строке, сохранение успешных записей при отклонении некорректных строк. Импорт не может автоматически установить статус «Действует»; записи с источником попадают «На проверку», без источника – в «Черновик».
- Экспорт карточек в CSV для ADMIN/EDITOR: реквизиты, полный текст карточек, статус, отметка проверки и число вложений. Экспорт не содержит бинарные файлы вложений и не заменяет резервную копию PostgreSQL/файлового хранилища.
- Поиск по названию, описанию, содержанию карточки, ключевым словам, товарной группе и реквизитам; фильтры по юрисдикции, типу и статусу. Виды материалов включают нормативные акты, товарные группы, инструкции, техническую документацию, известные ошибки, шаблоны, внутренние документы, бизнес-процессы и обзоры.
- Отдельное поле для полного текста рабочей инструкции или содержательной справки (до 50 000 символов); содержимое участвует в поиске и сохраняется в истории версий.
- При загрузке PDF, DOC/DOCX, XLS/XLSX, TXT и CSV текст автоматически извлекается в поисковый индекс (до 100 000 символов на файл). В карточке файла виден результат индексации.
- В списке документов администратор может запускать пакетную индексацию старых вложений партиями до 50 файлов за запрос (по умолчанию 25). В ответе показано количество успешно индексированных, частичных, пустых/неподдерживаемых и проблемных файлов, а также остаток очереди.
- При поиске карточки отображается метка «Найдено в приложенном файле», если поисковая фраза совпала с индексированным текстом вложения.
- Сканированные PDF и изображения PNG/JPG обрабатываются OCR через Tesseract на API-сервере (русский, кыргызский и английский языки). Распознанный текст помечается как OCR; его необходимо визуально сверять с оригиналом. Ограничение времени OCR – 15 секунд на распознаваемый объект, верхний порог размера изображения для OCR – 10 МБ.
- Старые вложения имеют статус «Текст не индексирован»; администратор может запускать пакетную индексацию, а ADMIN/EDITOR – переиндексировать отдельный файл без повторной загрузки.
- Текстовые индексы хранятся отдельно от исходного файла и не подменяют его содержимое.
- Раздел «Товарные группы» разделяет внешний контур МЗКМ РФ и внутренний контур ГАИС МТ КР.
- Даты документа и периода действия.
- Товарная группа, ключевые слова, связанные документы, официальный источник и комментарий проверки.
- Статусы: черновик, на проверке, действует, срок действия истёк, архив.
- История версий и авторы изменений, включая снимки ключевых метаданных и связанных документов.
- Каталог основных НПА РФ, КР и ЕАЭС добавляется миграциями Flyway `V4` и `V5`; новые записи первоначально имеют статус «На проверке».
- Ежедневная проверка даты окончания действия со сменой статуса на «Срок действия истёк».
- Главная панель показывает очередь актуальности: прошедшая дата «Действует по», отсутствие официального источника, статус ожидания проверки, а также отсутствующую или давнюю отметку подтверждения.
- Возраст проверки от 180 дней используется как внутреннее напоминание, а не как автоматическое признание нормативного акта утратившим силу.
- Дата последней проверки источника фиксируется при явном подтверждении статуса «Действует»; перевод карточки в «На проверку» не считается завершённой проверкой.

### Файлы
- Загрузка, скачивание и удаление вложений в авторизованном режиме.
- Допустимые форматы: PDF, DOC/DOCX, XLS/XLSX, CSV, TXT, PNG/JPG.
- Максимальный размер – 30 МБ на файл.
- Удаление карточки очищает связанные записи и сохранённые файлы.

### Доступ
- JWT-аутентификация.
- Роли: ADMIN, EDITOR, READER.
- Самостоятельная регистрация выключена.
- Администратор создаёт учётные записи, может отключать доступ и сбрасывать пароли.
- Пароли хранятся в виде BCrypt-хешей.

### Мониторинг источников
- Периодическая проверка заданных доверенных сайтов.
- Сравнение SHA-256-хеша первых 2 МБ ответа.
- Запись HTTP-статуса, даты проверки, ошибок и времени обнаружения изменения.
- Перенаправления отключены, проверка ограничена доменами из MONITOR_ALLOWED_HOSTS, локальные/частные IP блокируются.
- Найденное изменение – сигнал для ручной проверки сотрудником, а не юридическое заключение.

## Локальный запуск

Требуются Docker Desktop (или Docker Engine с Compose), Node.js 22+ и npm.

1. Скопируй шаблон окружения:
   - Windows PowerShell: Copy-Item .env.example .env
   - macOS/Linux: cp .env.example .env
2. Открой .env и замени DB_PASSWORD, JWT_SECRET и BOOTSTRAP_ADMIN_PASSWORD на уникальные значения. Пароль администратора должен быть не короче 12 символов; JWT secret – не короче 32 байт.
3. Запусти PostgreSQL и backend из корня репозитория: docker compose up --build
4. В другом терминале установи зависимости и запусти frontend: npm install, затем npm run dev.
5. Открой адрес Vite, показанный в терминале (обычно http://localhost:5173). Backend health endpoint: http://localhost:8080/api/health.
6. Войди логином и паролем из .env.

Первый администратор создаётся при первом запуске, только если заданы BOOTSTRAP_ADMIN_USERNAME и BOOTSTRAP_ADMIN_PASSWORD. Если аккаунт с таким логином уже существует, пароль автоматически не меняется. Не используй значения из шаблона как реальные пароли.

Остановка контейнеров: docker compose down. Данные PostgreSQL и файлы хранятся в Docker volumes и сохраняются при обычном перезапуске. Команда docker compose down -v удалит тома с данными – не используй её без резервной копии.

## Конфигурация Netlify

Для фронтенда:
- Build command: npm run build
- Publish directory: dist
- Environment variable: VITE_API_URL=https://адрес-развёрнутого-api

Для backend в переменной APP_CORS_ORIGINS укажи точный origin Netlify-сайта, например https://твой-сайт.netlify.app, вместе с локальным адресом, если локальная разработка ещё используется. Не добавляй завершающий путь.

Netlify хранит только frontend. В репозитории есть файл render.yaml – Blueprint для backend, PostgreSQL и постоянного диска под вложения на Render. Чтобы запустить Blueprint, выбери этот GitHub-репозиторий в Render Dashboard и проверь ресурсы и цену перед подтверждением: конфигурация включает оплачиваемый сервис API, managed PostgreSQL и persistent disk. При первоначальной настройке Render запросит сильный пароль администратора и точный origin Netlify для CORS.

После развёртывания:
1. Скопируй публичный адрес API из Render (он должен отвечать на /api/health).
2. В настройках Netlify добавь переменную VITE_API_URL со значением этого API URL.
3. Убедись, что APP_CORS_ORIGINS на Render содержит точный origin Netlify без завершающего пути.
4. Запусти новый deploy Netlify, чтобы VITE_API_URL попал в сборку.
5. Войди под логином и паролем администратора, установленными при первом запуске.

Для production используй HTTPS, резервное копирование базы, и проверь возможность восстановления файлов с постоянного диска. Не полагайся на временный диск контейнера для нормативных файлов. При необходимости мониторинга других официальных сайтов добавляй домены в MONITOR_ALLOWED_HOSTS после проверки доверенности.

При первом запуске backend с этими миграциями Flyway автоматически добавляет материалы, подготовленные по открытым официальным источникам:

- `V8__seed_operator_marking_workflows.sql` – 24 обзорные и операционные карточки: контуры КР/РФ/ЕАЭС, регистрация, GTIN/каталог, заказ и нанесение кодов, оплата, назначение оператора, правовая навигация, жизненный цикл товара в российской ГИС МТ, ЭДО, возврат и перемаркировка.
- `V9__seed_product_group_marking_guides.sql` – 7 карточек по детским игрушкам, кормам, косметике и бытовой химии, моторным маслам, расширениям перечня легкой промышленности, внешним группам и методическим материалам по алкоголю/табаку в КР.

- `V10__seed_mzkm_user_manual_workflows.sql` – 7 карточек по руководству пользователя МЗКМ v2.1 от 09.10.2026: единый список товарных групп, карточка товара, баланс/QR, заказ эмиссии с лимитом до 5 000 КМ, CSV серийных номеров, печать/нанесение, трансграничное перемещение и доступ.
- `V11__seed_mzkm_product_attributes.sql` – 2 карточки по атрибутам обуви, одежды/белья, парфюмерии, фотооборудования и молочной продукции из МЗКМ v2.1.
- `V12__unify_mzkm_product_groups_and_refresh_manual.sql` – исправляет 22 старые карточки, убирает ошибочное разделение групп МЗКМ на «внешние» и «внутренние», актуализирует сведения по версии 2.1 и добавляет 3 карточки по массовой регистрации/выгрузке Excel и атрибутам новых групп.
- `V13__seed_internal_marking_product_groups.sql` – добавляет в общую базу две отдельные карточки внутренней маркировки КР: «Алкоголь» и «Табак». Они не копируются в список десяти товарных групп МЗКМ v2.1. Отдельный режим УКМ для упакованной воды описывается независимо.
- `V14__seed_detailed_mzkm_product_groups.sql` – 10 подробных карточек по всем группам из титульного списка МЗКМ v2.1: атрибуты, кодовые источники, порядок операций, правовая область, сроки и оговорки.
- `V15__seed_product_group_legal_sources.sql` – 9 отдельных карточек нормативных актов РФ для обуви, одежды/белья, парфюмерии, фототехники, молочной продукции, кормов, косметики/химии, моторных масел и игрушек.
- `V16__archive_superseded_product_group_summaries.sql` – 7 старых кратких карточек из V9 переведены в архив; предыдущие редакции остаются в истории. Их заменяют подробные карточки V14 и нормативные карточки V15.
- `V18__seed_operator_tnved_reference_tables.sql` – добавляет 5 справочных карточек с таблицами ТН ВЭД, опубликованными на официальной странице новостей «Текшер»: 23 позиции для игрушек, 25 для косметики/бытовой химии, 7 для масел и технических жидкостей, позиция 2309 для кормов и 12 строк расширений лёгкой промышленности. Списки сохранены в исходной гранулярности и не объявлены полными актуальными юридическими перечнями.
- `V17__restore_mzkm_group_reference_cards.sql` – возвращает 6 карточек по товарам МЗКМ из архива в каталог «МЗКМ / товарные группы и коды ТН ВЭД», восстанавливает их полное содержание из истории версий и выставляет статус `UNDER_REVIEW`. Карточка по национальным материалам алкоголя и табака остаётся отдельно от МЗКМ.

Подробная карта источников и товарных групп: [`docs/PRODUCT_GROUP_DETAIL_RESEARCH_2026-10.md`](docs/PRODUCT_GROUP_DETAIL_RESEARCH_2026-10.md). Все новые карточки V14/V15 имеют статус `UNDER_REVIEW`; новости Текшер и руководство оператора не выдаются за исчерпывающий правовой перечень.


Новые карточки создаются со статусом `UNDER_REVIEW`. Это справочные материалы и ссылки, а не подтверждение актуальности каждой нормы или полного перечня ТН ВЭД. Перед переводом в статус «Действует» специалист должен сверить оригинал, редакцию, товарную позицию, исключения и дату начала обязанности.

Карта использованных официальных источников и ограничения исследования: [`docs/MARKING_KNOWLEDGE_SOURCES_2026-10.md`](docs/MARKING_KNOWLEDGE_SOURCES_2026-10.md).

### Модальные окна интерфейса

Подтверждение удаления документа/источника мониторинга, изменение статуса проверки источника и согласие на отправку материала в Groq оформляются внутри TEKSHER HUB. Браузерные `window.prompt()` и `window.confirm()` для этих сценариев не используются.

## ИИ-помощник по базе знаний

В разделе «ИИ-помощник» можно задать вопрос на русском или кыргызском языке. Backend ищет совпадения в карточках документов и проиндексированном тексте вложений, выбирает релевантные материалы и передаёт ограниченный контекст в Groq Responses API для подготовки ответа со ссылками вида [1], [2]. В интерфейсе отображаются найденные источники, статус карточки, выдержка и ссылка на официальный источник, если она указана.

- Endpoint: `POST /api/ai/ask`, JSON: `{"question":"Текст вопроса"}`.
- Доступен авторизованным ролям ADMIN, EDITOR и READER.
- Ограничение на вопрос – 2 000 символов; модель получает не более шести отобранных карточек и ограниченный текст их содержимого/вложений.
- Ответы основываются на найденных материалах; если ничего релевантного не найдено, API возвращает сообщение о недостатке данных без генерации ответа.
- Статус, юрисдикция, реквизиты и отметка проверки источника передаются модели вместе с материалом. ИИ не заменяет юридическую проверку, а статус карточки не является автоматическим юридическим заключением.
- Релевантные фрагменты содержимого передаются во внешний сервис Groq. Не используйте помощника для налоговой тайны, персональных данных или иных закрытых материалов без разрешения организации.
- История диалога пока хранится только в состоянии открытой страницы браузера и не сохраняется на сервере.

## Генерация краткого описания с ИИ

Серверный endpoint `POST /api/ai/summarize` готовит черновик описания из введённого текста и/или прикреплённого файла. Интеграция использует Groq Responses API. Для включения функции задай на backend переменную `GROQ_API_KEY`; по умолчанию используется модель `openai/gpt-oss-20b`, которую можно изменить через `GROQ_MODEL`.

- Получить ключ: [Groq Console](https://console.groq.com/keys).
- Локально: добавь ключ в локальный `.env` и пересобери backend командой `docker compose up --build -d api`.
- Render: в настройках сервиса `teksher-hub-api` открой Environment, добавь `GROQ_API_KEY` и сохрани изменения для redeploy. `render.yaml` содержит необязательную переменную.
- Храни ключ только на backend, не в чатах, коммитах или переменных Netlify.
- Бесплатный уровень имеет ограничения и может возвращать лимитирование; актуальные квоты смотри в [документации Groq](https://console.groq.com/docs/rate-limits).
- Текст документа отправляется во внешний сервис Groq. Не отправляй налоговую тайну, персональные данные или иные закрытые сведения без разрешения организации.
- ИИ создаёт только черновик. Он не проверяет юридическую силу, действующую редакцию или применимость нормативного документа; сотрудник обязан сверить описание с оригиналом.

## Переменные окружения backend

- DATABASE_URL – JDBC URL PostgreSQL; для Compose используется адрес сервиса db.
- DATABASE_USERNAME, DATABASE_PASSWORD – учётные данные базы.
- JWT_SECRET – секрет подписи токенов.
- JWT_EXPIRATION_MINUTES – время жизни токена.
- BOOTSTRAP_ADMIN_USERNAME, BOOTSTRAP_ADMIN_PASSWORD – начальный администратор.
- APP_CORS_ORIGINS – разрешённые origin фронтенда.
- UPLOAD_DIR – каталог вложений.
- MONITOR_ALLOWED_HOSTS – разрешённые домены для автоматических проверок.
- MONITOR_SCHEDULER_DELAY_MS, MONITOR_INITIAL_DELAY_MS – настройки расписания проверки.

## Ограничения и юридическая аккуратность

- Реальные нормативные документы не загружаются автоматически в каталог при первом запуске. Их нужно добавить, проверить и связать с официальным источником.
- Автоматический мониторинг отслеживает изменение ответа веб-сайта, но не выделяет юридически значимые изменения и не определяет, какая редакция нормы действует. Это остаётся задачей сотрудника.
- Статус «Действует» выставляется пользователем после проверки и не является автоматическим юридическим заключением.
- В режиме без VITE_API_URL frontend запускается как локальный демонстрационный интерфейс; карточки сохраняются в браузере, серверная авторизация не используется.
- Настройки хостинга, production secrets, CORS origin, резервное копирование и реальное развёртывание backend требуют выполнения в выбранном аккаунте хостинга.

Полные маршруты API и описание ролей см. в backend/README.md.


### Нормативный каталог

В начальном каталоге содержатся основные рамочные акты РФ и КР и ряд решений ЕЭК по отдельным товарным группам. Это стартовая подборка, а не заверенный исчерпывающий реестр всех актов и всех редакций. Импортированные карточки имеют статус «На проверке»: перед переводом в статус «Действует» ответственный сотрудник должен проверить официальный текст, действующую редакцию, сроки, перечень кодов и применимость к конкретной товарной группе.

Для расширения каталога используйте официальные источники:
- ЦБД правовой информации Минюста КР: https://cbd.minjust.gov.kg/search-docs/ru
- НПА Кабинета Министров КР: https://www.gov.kg/ru/npa
- Официальный портал правовой информации РФ: https://pravo.gov.ru/
- Евразийская экономическая комиссия: https://eec.eaeunion.org/

## Принцип платформы: единая база знаний

TEKSHER HUB предназначена быть единым рабочим источником знаний оператора маркировки товаров. Это не только каталог нормативных документов: в ней должны собираться все проверенные сведения, необходимые сотрудникам для ежедневной работы, обучения и принятия решений.

### Обязательные направления базы знаний

- **Нормативная база** – нормативные правовые акты, решения ЕЭК, редакции, даты вступления в силу, область применения и официальные источники.
- **Инструкции и памятки** – пошаговые руководства для сотрудников и участников по работе с системами и сервисами.
- **Бизнес-процессы** – последовательности действий, роли, входные данные, результат, сроки и исключения.
- **Техническая документация** – архитектура, интеграции, API, обмен данными, алгоритмы и технические ограничения.
- **Ошибки и решения** – точный текст ошибки, условия возникновения, причина, способ диагностики, решение и статус подтверждения.
- **Товарные группы** – требования и ограничения с разделением по юрисдикции, системе маркировки, периоду действия и источнику.
- **Шаблоны и делопроизводство** – согласованные формы писем, уведомлений, служебных записок, ответов и технических заданий.
- **Внутренние регламенты** – правила работы оператора, распределение ответственности, порядок согласования и взаимодействия.
- **Обучение сотрудников** – вводные материалы, чек-листы, практические сценарии и справочные карточки.
- **История изменений** – изменения нормативных требований, инструкций и рабочих процессов с указанием основания и даты.

### Правила качества информации

1. Каждая значимая запись должна иметь понятный тип, название, описание, ключевые слова и ответственного за актуальность, если эти поля предусмотрены рабочим процессом.
2. Нормативные сведения должны содержать юрисдикцию, официальный источник, реквизиты, дату документа и сведения о периоде действия, когда они известны.
3. Статусы «На проверке» и «Действует» нельзя считать взаимозаменяемыми. Материал не должен подаваться как проверенный до подтверждения ответственным сотрудником.
4. Инструкции и бизнес-процессы должны указывать, к какой системе, роли и ситуации они относятся, а также дату последней проверки.
5. Изменение документа или инструкции должно сохранять историю редакций, когда это поддерживается системой.
6. Необходимо явно различать подтверждённые факты, внутреннюю практику, рабочие гипотезы и сведения, ожидающие проверки.
7. Материалы должны находиться поиском не только по названию, но и по содержанию, ошибкам, товарной группе, системе, ключевым словам и связанным документам.
8. При наличии нескольких контуров информация должна быть однозначно отнесена к РФ / МЗКМ, КР / ГАИС МТ или ЕАЭС. Нельзя автоматически переносить требования одной юрисдикции в другую.

### Целевой принцип поиска

Сотрудник должен иметь возможность начать с практического вопроса, например «почему не заказывается код», «как исправить карточку товара» или «какие требования действуют для товарной группы», и получить связанную подборку: инструкцию, нормативное основание, известные ошибки, шаблоны и связанные материалы. Для этого база должна постепенно перейти от хранения отдельных карточек к связанной системе знаний.

### Поэтапное развитие

1. Создать полный перечень типов материалов и единые правила оформления карточек.
2. Собрать и проверить имеющиеся документы, инструкции, файлы, шаблоны и решения из рабочих источников.
3. Разнести материалы по юрисдикциям, системам, товарным группам и бизнес-процессам.
4. Настроить связи между нормативными актами, инструкциями, ошибками и процессами.
5. Добавить полнотекстовый поиск по содержимому файлов, где это технически возможно.
6. Ввести процесс проверки актуальности, назначения ответственных и фиксации изменений.
7. Постепенно автоматизировать мониторинг официальных источников, сохраняя обязательную человеческую проверку юридически значимых изменений.

**Целевой результат:** сотрудник использует TEKSHER HUB как основное место поиска рабочих знаний. При этом база не подменяет официальные правовые источники: она помогает найти проверенную информацию, понять её применимость и перейти к первоисточнику.
